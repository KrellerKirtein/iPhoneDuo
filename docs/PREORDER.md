# 定时预购与订单恢复

## 定时流程与使用约定

- 闭店兼容：启用准备、测试和临开售预热遇到 HTTP 503 或明确的预购闭店页时可延后。
  测试尚无提交意图时记录为 `skipped`，继续等待正式开售；恢复同一计划不补做已跳过的测试。
  认证与订单基线必须在正式提交前补齐，正式阶段仍按执行窗口和 `Retry-After` 恢复。
  明确认证失败、未知页面、测试提交结果不明仍停止；不自动删除购物袋中的其他 SKU。
  验证覆盖闭店贯穿三个准备阶段、开放后只建正式单、测试提交后 503 防重、跳过状态恢复与限流跨阶段等待。
- 约定单账号、每阶段单 SKU、1 件；启用前清空购物袋，等待期间不在其他设备修改该账号购物袋。
- 新计划明确授权至多两笔订单：开售前 5 分钟尝试创建一笔 `MJY64CH/A`（iPhone 18 Pro Max
  256GB 黑色）测试订单，1 件、不带 AppleCare、总额不超过 10,999 元，沿用正式计划的地址和付款方式，
  不付款、不自动取消；到点再创建正式订单。旧计划未授权测试时维持原有单笔购买范围。
- 测试记录嵌入同一个账号计划文件，分别保存提交意图、订单基线和结果。测试结果不明时只查单；
  测试已确认后恢复不重复建单，也不把测试订单当成正式订单。测试创建后沿用已冻结计划。
- 测试最晚于开售前 1 分钟停止提交；过晚启用时跳过测试，仍在正式执行窗口内则继续抢购。已确认测试的计划可继续恢复正式购买。
- 开售前 10 秒尝试读取购物袋、检查登录并准备目标商品加购信息；商城暂不可用时延后至开售。
  首轮仅复用同一会话中不超过 15 秒的准备结果，
  且令牌仍须与当前 Cookie 一致。失败后重新读袋、读取当前令牌，不重复追加数量。
- 正式开售后的前 30 秒内，可恢复错误按 1 秒间隔，之后至 120 秒按 2 秒，再之后按 5 秒；
  服务端 `Retry-After` 优先，执行窗口耗尽停止。提交结果不明继续只查单。
- 配送优先；明确不可配送时按预设门店顺序备选。不比较到货日期，也不设到货日期门槛。
- 验证：离线覆盖两笔订单身份、防重和恢复、预热复用/过期、限流等待、固定履约顺序；
  运行 Worker 回归、前端构建和定向 UI 测试。不在开发验证中使用真实账号建单。

## 目标与边界

默认目标时间为
`2026-10-16T20:00:00+08:00`，时间字段必须携带时区。每个账号配置一个购买计划，
送货优先，在官网明确没有可用配送服务时尝试用户指定的备选门店。
自动核对 SKU、数量、金额上限和收货信息，创建订单后停止，付款由用户完成。
未知接口结构、验证要求和订单提交结果不明都不能解释为库存不足。

此模式是用户预先授权的自动提交；它覆盖 PRODUCT.md 中旧版“逐笔人工确认”的限制，
只对新增计划生效，普通购买保留原确认界面。无需迁移旧账号配置。
不增加多账号并发购买、自动付款、代理轮换或验证码绕过。分期建单见 [分期选项](INSTALLMENTS.md)。

## 数据流

前端提交计划 → Rust 原有账号独占队列 → Python 原有账号文件锁 →
校验并保存账号级计划 → 提前认证与读取订单基线 → 等待至开售前 5 分钟 →
已授权的测试建单（独立提交意图与结果）→ 开售前 10 秒预热正式商品 →
到点加购/核对购物袋 → 送货或白名单门店 → 核对订单 → 持久化正式提交意图 →
仅一次正式提交 → 确认订单身份与金额 → 返回待付款信息。

启用时先尝试检查认证并读取订单基线；商城关闭或 503 时允许延后，但正式提交前必须补齐。
测试订单成功后，其订单号加入正式购买基线。
开售前 10 秒再次检查会话并读取正式购物袋、商品页和加购令牌，到目标时间才加购正式商品。
本地 15 秒复用窗口是程序约定，不是官网令牌有效期承诺；Cookie 变化或缓存过期则重新准备，
请求失败后先重新读袋再恢复。测试单只能证明测试时会话可完成结账，不能保证之后服务端不会要求认证。
用户过晚启动或官网要求验证码时，准备可能延后；测试截止为开售前 1 分钟，正式截止由执行窗口决定。
闭店页或 503 导致未提交的测试跳过后，状态和原因会保存并显示，不能据此宣称 Cookie 已通过实测。
预热遇到暂时网络错误也可延后；服务端跨阶段的 `Retry-After` 会保存，正式开售不能提前越过等待要求。
提交前可恢复错误按阶段使用 1/2/5 秒间隔，服务端 `Retry-After`（秒数或 HTTP 日期）优先，总时长由窗口限制。
只恢复网络异常、购物袋尚未就绪、明确无可用履约方式、已识别闭店页和 429/502/503/504；
未知模型、认证失败、错误商品/数量/金额不当作缺货重试。

计划保存在账号目录 `preorder.json`，包括版本、计划参数、地址快照、阶段、
提交前订单编号基线、已核对商品、订单结果与提交时间，以及独立的 `test_order` 测试记录。
写入采用原子替换并 flush/fsync。账号文件锁覆盖读改写和整个执行过程。
日志不记录密码、Cookie 或支付链接。

## 失败与兼容性

- 定时任务需要应用/本地服务运行，电脑联网且保持唤醒，不安装系统计划任务。
- 等待可以取消；重启后由“恢复已保存计划”显式继续。超过执行窗口不补发订单。
- 只读请求可有限重试；加购失败后先读购物袋核对，不盲目追加数量。
- 下单前每次恢复重新读取页面模型和令牌，不重放旧表单。
- 提交前落盘 `submitting`；一旦到达该阶段，取消、网络错误或进程退出都只允许查单。
- 没查到订单不能证明未创建，不自动清除提交记录，也不重新提交。
- 用提交结果中的订单号和金额确认待付款结果。查单恢复只在基线以外有唯一的
  完整商品名称和数量匹配，且前后订单列表均未分页截断时确认查到匹配订单；
  订单列表没有 SKU、创建时间和付款状态，不把查单匹配当作精确的交易关联或支付成功。
  历史订单有更多页时仍允许首次创建，但提交超时后保持待确认，须在官网人工核对。
- 同账号已有提交中/待确认/已确认的正式订单时，重复启动返回原结果或执行查单，
  不创建第二笔正式订单。测试单提交后冻结原计划；恢复先确认测试，再执行尚未提交的正式购买。
  测试和正式订单的已提交记录（包括已确认）均阻止普通购买/结算绕过保护。
  当前版本没有自动清除或重置已提交计划入口，每账号用于本次购买目标。
- 没有可用送货或备选门店时在窗口内等待；缺少必填字段、未知预约结构或联系人要求验证时停止。
- 取货按白名单顺序选择可用门店，再按官网顺序选第一个非受限预约时段；无时段则尝试下一家。
  日期和签名必须来自当前响应，不推算日期、不伪造签名。支持当前已实现的模型结构，接口变化时停止。
- 地址采用计划启用时的完整本地快照，配送/地址步骤提交对应省市区、街道及联系人，
  复核页核对街道；取货核对门店名称。不会默认改用官网另一条已保存地址。
- 每个阶段仅购买该阶段指定 SKU 的 1 件，其他购物袋商品不会自动删除或一起结账。
  约定测试订单成功后官网已清空购物袋；仍有测试商品或其他商品时停止，须人工处理后恢复。
- 老计划缺少 `test_order_authorized` 时不增加测试订单；新界面授权同时覆盖一笔测试与一笔正式订单。
  测试订单的付款链接不写入任务付款文件，界面区分测试与正式订单号，避免误付测试订单。
- 该实现没有可用的 Apple 创建订单幂等键，不能保证远端恰好一次。
  保护限于此版本应用、同一账号目录；官网、旧 CLI、其他机器或删除重建账号不受该记录约束。

## 使用方式

1. 在“本地配置”选择实际使用的账号，保存完整联系人、省市区和详细地址；取货联系人沿用此人。
2. 在工作台选择目标 SKU，在“定时预购”核对北京时间和执行窗口。当前计划固定购买 1 件，
   上方普通购买的数量输入不影响定时计划。
3. 订单总额上限可留空，留空则不限制金额；填写时须为大于零的人民币金额，结算总额超过上限时停止下单。
   无论是否设置上限，仍须识别有效的订单总额，并核对下单后的金额。已保存计划中的数值上限继续生效。
   需要取货备选时按顺序填写 `R` 开头的门店编号及证件后四位。
   编号输入框下方的“查询门店编号”支持按城市、店名、地址或编号搜索，显示店名、编号和地址，
   点击“添加”按优先顺序填入，重复门店不可再次添加，最多 10 家；修改门店后需要重新勾选授权。
   查询使用内置的官网中国大陆门店目录快照，无需登录或进入结账，界面标明目录更新时间；
   目录不代表实时库存。未收录门店仍可手动填写编号。
   门店编号只约束当前搜索城市内官网返回的门店，城市取自送货地址。
4. 核对测试商品与 10,999 元测试上限，勾选两笔订单授权后启用，按需完成密码/验证码。
   建议至少提前 5 分钟启动，测试提交窗口为开售前 5 分钟至前 1 分钟。保持应用或本地服务运行，电脑不休眠。
5. 测试单成功后继续等待正式抢购，不付款、不自动取消测试订单。
   商城未开放、503 或启用过晚导致测试跳过时，界面会明确提示；继续正式抢购，不补建测试单。
   正式订单成功显示订单号及金额后程序停止，不访问支付平台；原有支付宝方式可手动获取二维码，分期订单由用户在官网订单页另外付款。
6. 超时或重启后点击“恢复已保存计划”。提交前且仍在窗口内可继续，已提交则只查询订单。

支持原有支付宝、招商银行分期、支付宝信用卡分期（农业银行卡由用户在支付宝选择），个人电子发票规则不变。不增加信用卡直接扣款，具体方式和期数须经官网当前订单模型确认。

门店目录来源：[Apple 中国大陆零售店列表](https://www.apple.com.cn/retail/storelist/)。
维护者运行 `powershell -NoProfile -File scripts/update-retail-stores.ps1` 可从官网更新
`src/retail-stores.ts`，再运行 `pnpm exec prettier --write src/retail-stores.ts` 并重新构建。
官网结构异常时脚本停止并保留原目录；仅影响目录更新，不影响手动填写及已有购买计划。

## 验证里程碑

1. 固定时区、时间窗口、参数与自动核对的离线测试。
2. 送货优先、明确不可配送时转白名单取货；未知/网络错误不误切换。
3. 请求已被接受但响应超时、重启恢复、取消、重复启动、订单延迟可见测试。
4. 前端定时授权、恢复入口与待确认显示测试，TypeScript 构建及原回归。
5. 实际账号、首发接口与峰值网络行为仍需用户环境验证；离线通过不代表抢购成功率。

## 恢复与回滚

取消任务即可停止等待或提交前执行。提交阶段取消不能撤销远端订单；使用恢复入口查单。
升级/回滚前保留账号目录，尤其 `preorder.json`。不要删除该文件来解除待确认状态。
回滚到旧版本会失去新增防重保护，必须先在官网核对订单再使用旧购买流程。

## 离线复核

具备 Node、pnpm、Rust 和 Python 开发环境后，在仓库根目录运行：

```powershell
pnpm build
pnpm test:worker
cargo test --manifest-path local-web/Cargo.toml --locked
$env:DUO_UI_FIXTURE_ONLY = '1'
$env:DUO_UI_BROWSER_CHANNEL = 'chrome' # 使用本机 Chrome；省略则使用 Playwright Chromium
pnpm test:ui --workers=4
```

`DUO_UI_FIXTURE_ONLY` 仅切换合成 API 界面测试的启动方式，正常使用仍运行 `pnpm dev:web`。
新增测试覆盖真实 Python 控制流与合成商城模型、进程重启读取已确认记录、提交意图写入失败、
提交后超时/取消、延迟查单、加购已接受但读袋超时、金额不一致，以及普通购买回归。
Rust 测试使用与桌面共享的 engine；没有以此代替 Windows Tauri 成品打包验证。

本机临时 Rust 工具链放在工作树 `artifacts/toolchain`，未写入系统 PATH。
在此工作树复用它运行 `cargo` 或 `pnpm dev:web` 时先设置：

```powershell
$env:CARGO_HOME = Join-Path $PWD 'artifacts/toolchain/cargo'
$env:RUSTUP_HOME = Join-Path $PWD 'artifacts/toolchain/rustup'
$env:PATH = "$env:CARGO_HOME/bin;" + $env:PATH
```
