## 2026-10-16：商城 503 与账号误移除

- 当日 15:18 的账户查询先收到 HTTP 503，随后完整登录中的浏览器页面准备失败；
  原逻辑把两次失败连成“重新认证失败”，触发账号移除。浏览器异常未保留 HTTP 状态，进一步掩盖了服务端异常。
- 匿名只读访问复现：首页 200，购物袋与账户页 503；响应带有 `coversModeType: preorder_full`，
  内容哈希与原失败日志相同，表明商城处于预购准备页面，不能据此判定账号凭据失效。
- 修复：查询中的网络、限流和服务异常直接返回；浏览器准备异常单独分类并保留页面名称和 HTTP 状态；
  此类异常不触发账号移除、保险库密码清理或认证 Cookie 清理。不改变明确认证失败的原有处理。
- 验证：先用离线用例复现错误回退及状态丢失；修复后 Worker 共运行 293 项测试，292 项通过、1 项 Windows 不适用测试跳过。
  15:26 使用独立临时账号目录运行真实 Worker 的匿名账户查询，收到 503，返回 `account_invalid=false`，
  未提示密码、未启动浏览器、保留认证文件。记录位于本地 `artifacts/login-unavailable-live-check.json`。
- 未操作真实账号登录或购买，未修改真实账号注册表。此前已被误移除的账号不会自动重新启用；
  当前待添加账号仍需在商城恢复后完成登录。若开售前测试时商城仍返回 503，真实测试订单也无法创建。

## 约束

- 一个真实 Apple 账号只登记一个 profile；不同账号并行，同账号串行。
- 程序只打包一份 Python worker，按任务启动实例；不同账号不设并行数量上限，同账号保留独占执行。
- 用户主动点击才请求 Apple；开发验证使用合成数据与离线测试。
- 保留原 SRP / SSI / authx / Cookie 更新流程，不自动重试下单请求。
- 提交订单前展示服务端返回的商品、数量、总价并要求用户明确确认。
- worker 通过私有管道接收密码/验证码，不通过命令行参数或日志传递。
- CLI 和桌面版分别适配交互；桌面版不解析中文终端输出来驱动业务。
- Windows 构建只能以 Windows CI/实机结果确认；macOS 成功不能代替 Windows 验证。
